# قرارداد داده — گام دوم

مرجع اجرایی قرارداد، فایل `config/schema.json` با نسخهٔ ۱ است. این قرارداد
اختصاصی پروژه است و استاندارد عمومی JSON Schema نیست. بارگذاری آن فقط صحت
تنظیمات قرارداد را بررسی می‌کند؛ اجرای اعتبارسنجی رکوردها گام بعدی است.

برای خروجی این مرحله ۱۷ ستون منبع انتخاب شده‌اند که برای تحلیل زمان بسته‌شدن،
روند ماهانه، مقایسهٔ دسته‌ها و اتصال جمعیت لازم یا مفیدند. فیلدهای دیگر منبع،
از جمله جزئیات آدرس و داده‌های مکانی جایگزین، در فایل خام کامل محفوظ‌اند.
تبدیل به این نمای انتخابی فقط هنگام اجرای مرحلهٔ پردازش اتفاق خواهد افتاد.

| ستون | نوع منطقی | خالی مجاز؟ | سیاست و دلیل |
|---|---|---|---|
| `unique_key` | string | خیر | شناسهٔ متنیِ رقمی و کلید یکتای کل داده؛ فقدان یا شکل نامعتبر، قرنطینه |
| `created_date` | datetime | خیر | تاریخ ثبت معتبر و داخل دامنه؛ برای تعیین ماه و محاسبهٔ مدت ضروری است |
| `closed_date` | datetime | بله | خالی حفظ شود؛ مقدار غیرخالیِ نامعتبر یا قبل از ثبت، قرنطینه |
| `agency` | string | خیر | مسئول پرونده؛ نبود مقدار قرنطینه، بدون محدودکردن آژانس به نمونهٔ NYPD |
| `agency_name` | string | بله | برچسب توصیفی؛ مقدار نامعتبر به null با پرچم تبدیل شود |
| `complaint_type` | string | خیر | مقادیر مجاز از `source.complaint_types`؛ مقدار خالی یا خارج از دامنه، قرنطینه |
| `descriptor` | string | بله | جزئیات تکمیلی؛ فقدان آن نباید مانع تحلیل نوع شکایت اصلی شود |
| `status` | string | بله | وضعیت نامشخص به null علامت‌گذاری‌شده؛ ناسازگاری با تاریخ بسته‌شدن فقط پرچم بخورد |
| `incident_zip` | string | بله | پنج رقم با حفظ صفر ابتدایی؛ placeholder یا شکل نامعتبر به null با پرچم |
| `borough` | string | بله | یکی از پنج borough پس از یکسان‌سازی حروف؛ نامعتبر به null با پرچم |
| `latitude` | float | بله | عدد متناهی در بازهٔ ۹۰- تا ۹۰؛ مقدار نامعتبر به null با پرچم |
| `longitude` | float | بله | عدد متناهی در بازهٔ ۱۸۰- تا ۱۸۰؛ مقدار نامعتبر به null با پرچم |
| `location_type` | string | بله | دستهٔ کمکی موقعیت؛ بدون حدس‌زدن دستهٔ جایگزین |
| `open_data_channel_type` | string | بله | کانال ثبت؛ `UNKNOWN` یک دستهٔ قابل نگهداری است، نه null |
| `resolution_description` | string | بله | متن اداری؛ خالی حفظ شود و وجود متن معادل حل واقعی مشکل نیست |
| `resolution_action_updated_date` | datetime | بله | تاریخ تکمیلی؛ مقدار نامعتبر به null با پرچم، جایگزین closed_date نشود |
| `city` | string | بله | برچسب locality؛ از borough یا ZIP برای آن مقدار نسازیم |

همهٔ فیلدهای انتخاب‌شده در نمونهٔ فعلی از نوع JSON string بودند. نوع هدف
مختصات float و نوع منطقی تاریخ‌ها datetime است. JSON تاریخ بومی ندارد؛ در خروجی
JSONL آینده تاریخ معتبر با قالب ISO و دقت میکروثانیه ذخیره خواهد شد. اعداد
و رشته‌ها به‌جای یکدیگر پذیرفته نمی‌شوند مگر source_types صریحاً آن را مجاز کند.

## تفاوت خالی‌بودن با حضور ستون

`nullable` دربارهٔ مقدار نهایی یک رکورد است. `required_presence` دربارهٔ
ساختار یک batch است. چهار فیلد شناسه، تاریخ ثبت، آژانس و نوع شکایت باید در
ساختار ورودی حضور داشته باشند. کلیدهای اختیاری ممکن است به دلیل nullبودن در
JSON منبع حذف شده باشند؛ غیبت آن‌ها به‌تنهایی اثبات تغییر schema نیست.

در آماده‌سازی آینده، فاصلهٔ ابتدا و انتهای متن حذف می‌شود و تشخیص عبارت‌های
خالی، نسبت به بزرگی و کوچکی حروف حساس نیست. تبدیل حروف به بزرگ فقط برای
ستون‌هایی انجام می‌شود که قرارداد آن را تصریح کرده است. اصلاحات همراه پرچم‌اند.

`on_invalid` رفتار با مقدار غیرخالی و نامعتبر را مشخص می‌کند؛ رفتار مقدار خالی
از `nullable` می‌آید. برای نمونه، closed_date خالی مجاز است ولی closed_date
غیرقابل‌تفسیر به قرنطینه می‌رود. مقدار مکانی یا توصیفیِ قابل‌اصلاح، پیش از
کنترل قرارداد نهایی به nullِ مجاز همراه پرچم تبدیل می‌شود؛ مقدار خام محفوظ است.

## قواعد بین ستون‌ها

- دامنه بر اساس created_date است: شروع شامل، پایان غیرشامل. تاریخ بسته‌شدن
  می‌تواند پس از پایان این بازه باشد. فیلترهای شکایت و منطقه از تنظیمات می‌آیند.
- مدت ثبت‌شدهٔ بسته‌شدن، اختلاف closed_date و created_date بر حسب ساعت است.
  تاریخ خالی مدت null می‌دهد؛ تاریخ‌های برابر مدت صفر می‌دهند؛ فاصلهٔ منفی
  قرنطینه می‌شود. مدت مثبت طولانی در این مرحله با سقف دلخواه حذف نمی‌شود.
- تاریخ‌ها بدون offset تفسیر می‌شوند؛ فرض UTC و تبدیل خودکار منطقهٔ زمانی
  نداریم. این معیار زمان ثبت‌شدهٔ اداری است.
- شناسه در کل دادهٔ پذیرفته‌شده یکتا خواهد بود. از میان رکوردهای منفرد معتبر،
  اولین رخداد در ترتیب فایل‌ها می‌ماند. تکرار کامل JSON خام با ترتیب کلیدهای
  یکسان‌سازی‌شده، `DUPLICATE_RECORD` و محتوای خام متفاوت با همان شناسه،
  `DUPLICATE_KEY_CONFLICT` می‌گیرد. این سیاست ادعای انتخاب جدیدترین نسخه ندارد.
- شکایت مشابه با شناسهٔ متفاوت، خودکار تکراری نیست.
- اگر فقط یکی از latitude و longitude قابل استفاده باشد، هر دو با پرچم خالی
  می‌شوند. حدود جهانی مختصات به‌تنهایی عضویت در محدودهٔ NYC را اثبات نمی‌کند.
- الگوی ZIP فقط شکل پنج‌رقمی را کنترل می‌کند. پوشش واقعی مرجع جمعیت و تفاوت
  ZIP/ZCTA در مرحلهٔ اتصال ارزیابی می‌شود. borough موجود هم حفظ می‌شود تا آن
  مرحله بتواند آن را با نگاشت مستقل مقایسه کند.
- ناسازگاری status و closed_date پرچم می‌گیرد؛ از روی status تاریخ نمی‌سازیم.

## ستون‌های مشتق‌شدهٔ تعریف‌شده

| ستون | تعریف |
|---|---|
| `created_month` | ماه تاریخ ثبت، به شکل YYYY-MM |
| `closure_hours` | مدت ثبت‌شده تا بسته‌شدن؛ nullable و بدون مقدار منفی |
| `has_recorded_closure` | وجود closed_date قابل‌استفاده؛ اثبات حل مشکل نیست |
| `quality_flags` | فهرست مرتب پرچم‌های کیفیت و اصلاحات اختیاری |

در این گام فقط قرارداد و نمایش آن نهایی شده است. هیچ خروجی پذیرفته‌شده یا
قرنطینه‌ای تولید نمی‌شود و آستانهٔ قرنطینه و اجرای آن به گام مربوط واگذار می‌شود.
